# Phase IV — Full Transition: UIAO-Assisted Detailed Reference

## How to read this document

This document is the UIAO-assisted detailed reference for the full transition phase of Windows endpoint governance — the phase in which net-new devices are procured, provisioned, and operated entirely within the cloud-native Microsoft Entra ID and Microsoft Intune surfaces, with no on-premises Active Directory relationship. It parallels the structure of the without-UIAO companion ([`without-uiao-full-transition.md`](without-uiao-full-transition.md)) and describes, section by section, how the organization's internal UIAO governance framework operationalizes the Intune-first model into a repeatable, evidence-bearing, drift-resistant process.

The full transition phase is where UIAO is most architecturally significant, because the cloud-native operating model has fewer built-in constraints on device identity, organizational positioning, and lifecycle than the on-premises model it replaces. Microsoft Entra ID, Microsoft Intune, and Conditional Access provide the operational mechanism; UIAO provides the canonical specification, the process discipline, and the audit posture that bind those mechanisms into a governed system. Without UIAO, the cloud-native model is operationally functional but governance-thin; with UIAO, the cloud-native model becomes the most fully governed of any phase in the modernization journey.

## What UIAO is

UIAO is the organization's internal governance substrate for identity, device management, and access control. In the full transition phase, UIAO sits across Microsoft Entra ID, Microsoft Intune, the upstream procurement and asset management systems, the human-resources information technology system, and the per-platform vendor systems that handle pre-registration (Microsoft Cloud Solution Provider channel for Windows Autopilot, Apple Business Manager for macOS and iOS/iPadOS, Android Zero-Touch portal, Samsung Knox Mobile Enrollment, Azure Arc onboarding for servers). The substrate provides canonical organizational positioning (OrgPath), continuous drift detection, evidence emission, and the canonical specification that drives every downstream system from a single source of truth.

UIAO does not modify the behavior of Windows Autopilot, Microsoft Intune policy delivery, Microsoft Entra ID authentication, or Conditional Access policy evaluation. The device-side out-of-box experience is identical whether UIAO is present or not; the user signs in, the device joins Entra ID, Intune enrolls the device, configuration profiles deliver, and the desktop appears. What UIAO changes is the upstream specification (the Autopilot profile, the compliance policy, the dynamic group memberships, the Conditional Access scope are all generated from OrgPath rather than authored independently) and the downstream attestation (the evidence ledger captures every governance event in structured form).

## The full transition phase reviewed

The without-UIAO companion describes the full transition architecture in detail. Net-new devices are procured directly from manufacturers or resellers participating in the appropriate pre-registration program, with hardware identifiers (hardware hash for Windows, serial number for Apple, IMEI for Android) registered into the organization's tenant before the device ships. On first power-on, the device contacts its pre-registration service (Windows Autopilot, Apple Business Manager Automated Device Enrollment, Android Zero-Touch, and so on), receives its assigned profile, walks the user through a corporate-branded sign-in to Microsoft Entra ID, performs a native cloud join, and automatically enrolls into Microsoft Intune. Configuration profiles, security baselines, compliance policies, and required applications apply during the Enrollment Status Page. The user reaches the desktop on a device that is already governed end-to-end.

Identity is exclusively cloud-resident. The device object exists in Microsoft Entra ID and nowhere else. Authentication uses primary refresh tokens bound to the device's Trusted Platform Module. Configuration flows through Microsoft Intune as Mobile Device Management policies expressed against the Windows Configuration Service Provider surface. Compliance evaluation is continuous and feeds into Conditional Access. Application delivery uses the Win32 app model, the Microsoft Store integration, and the Microsoft 365 Apps integration. Updates are governed by Windows Update for Business policies. Endpoint security uses Microsoft Defender for Endpoint integrated into Microsoft Intune. On-premises reach-back, where required, uses Microsoft Entra Kerberos (Cloud Kerberos Trust) to issue Kerberos tickets for legacy resources.

## How UIAO is layered onto the full transition

UIAO is most architecturally integrated with the full transition phase because the canonical specification drives every operational decision. The legacy phase used UIAO as an observational overlay; the full transition phase uses UIAO as the authoritative upstream specification source. Autopilot deployment profiles are generated from canonical specification rather than authored in the Intune admin center. Compliance policies are projected from the canonical compliance specification. Dynamic security groups are generated from OrgPath. Conditional Access policies have their scope derived from OrgPath classifications. Per-platform vendor configurations (Apple Business Manager device assignments, Android Zero-Touch configurations, Azure Arc resource group placements) are derived from the canonical specification with their associated OrgPath classifications.

The drift engine continues to operate, observing the actual cloud-native state and comparing it against the canonical specification. Drift findings surface within hours of occurrence. The reconciliation engine spans the cloud-native systems and the upstream procurement and human-resources systems, ensuring that the chain from procurement decision through deployment through ongoing operation remains coherent. The evidence ledger captures every event in the chain.

## The canonical five-phase Intune-first onboarding process

The first major UIAO contribution in the full transition phase is the formalization of onboarding as a five-phase canonical process: Procure, Pre-stage, Position, Provision, and Validate. The process is anchored in canonical architectural decision records ADR-067 and ADR-071 in the organization's internal repository.

**Procure** captures the procurement decision and the organizational context for the device. At purchase-order issuance, the OrgPath assignment for the future device is determined: business unit, region, asset class, ownership classification, security tier, cost center, and assigned user where known. The canonical device record is created before the vendor receives the order, with the OrgPath assignment in place. The procurement-side specifications (which vendor, which model, which warranty, which support contract) are recorded alongside the governance-side specifications (which OrgPath, which Autopilot profile, which compliance policy class).

**Pre-stage** registers the device into the appropriate vendor pre-registration surface before the device leaves the vendor's possession. For Windows, this is Windows Autopilot registration through the Cloud Solution Provider API. For macOS and iOS/iPadOS, this is Apple Business Manager device assignment. For Android, this is Android Zero-Touch portal registration or Samsung Knox Mobile Enrollment depending on the device class. For Azure Arc-managed servers, this is the Azure Arc onboarding token. UIAO verifies that the registration completes before the device ships, with the procurement guide's PO clause enforced contractually and the verification step performed automatically through the relevant vendor API.

**Position** assigns the device's full operational position: which dynamic security groups it belongs to (derived from OrgPath), which Conditional Access scope it falls under (derived from OrgPath), which compliance policy applies (derived from OrgPath security tier), which configuration profile applies (derived from OrgPath and asset class), which application set is assigned (derived from OrgPath role), which update ring assignment is in place (derived from OrgPath and migration cohort), and which on-premises reach-back resources are accessible via Cloud Kerberos Trust (derived from OrgPath classification). The positioning decisions are all derived from the OrgPath assignment made in the Procure phase; no per-device authoring is required at Position time.

**Provision** is the device-side Autopilot (or Apple Business Manager ADE, Android Zero-Touch, Azure Arc onboarding) experience. The device boots, contacts the pre-registration service, receives the profile that was derived from OrgPath at Position time, joins Microsoft Entra ID, enrolls into Microsoft Intune, and applies the canonical configuration. Provision is end-user-facing but fully determined by upstream decisions.

**Validate** verifies that the provisioned device matches its canonical specification end-to-end: the Microsoft Entra ID device object has the expected OrgPath; the Microsoft Intune managed device record has the expected compliance state; the assigned groups, Conditional Access scopes, configuration profiles, and applications are in the expected state; the device has emitted the expected evidence to the ledger. Successful Validate admits the device to production operation. Failed Validate routes the device through a remediation workflow.

The five-phase process is the canonical onboarding doctrine for the organization. Each phase has specified inputs, outputs, evidence emissions, and exit criteria, all documented in `src/uiao/modernization/intune-first-onboarding/`.

## OrgPath assigned at procurement time

The second major UIAO contribution, and the single most consequential one in the full transition phase, is that OrgPath is determined at procurement time, written to the canonical device record before the device ships, and inherited automatically by every downstream system. The Autopilot deployment profile, the Apple Business Manager device assignment, the Zero-Touch configuration assignment, and the Azure Arc resource group placement are all derived from OrgPath. The dynamic security group memberships that drive Conditional Access scoping and compliance policy targeting are derived from OrgPath. The user assignment, the asset class, the cost center, and the business unit are all encoded in OrgPath and are present on the device record before the device is powered on.

The device emerges from out-of-box experience already in the right groups, already inside the right Conditional Access scope, already evaluated against the right compliance policy, already governed by the right configuration profile. Without UIAO, organizational positioning is assigned post-hoc — after the device has reached the user, by humans inspecting the device and assigning it to security groups based on context. The post-hoc assignment is operationally expensive (per-device touch by an engineer) and error-prone (devices missed entirely, devices assigned to wrong groups, devices that drift out of their assignment over time). With UIAO, the assignment is made once, at the procurement decision moment, and propagates automatically.

## Autopilot profile generation from canonical specification

The third major UIAO contribution is generation of Autopilot deployment profiles (and the per-platform equivalents for non-Windows devices) from the canonical specification. An Autopilot deployment profile in Microsoft Intune specifies the join type, the user-experience mode, the username hidden or shown, the language and region defaults, the device naming template, the Enrollment Status Page behavior, and several other behaviors. Without UIAO, the profile is authored in the Intune admin center as a configuration artifact, and the organization typically has a small number of profiles (two to five) corresponding to broad device classes.

With UIAO, profiles are generated from the canonical specification on demand. The specification expresses the intent ("devices in business units handling controlled unclassified information, with security tier high, asset class corporate-issued knowledge-worker laptop, should provision with the corporate-branded user-driven experience, with mandatory pre-provisioning of the security baseline, the BitLocker policy, the conditional access registration, and a specific set of pre-installed applications"), and the corresponding Autopilot profile is generated. Profile changes are made by amending the canonical specification; the projection into Intune updates accordingly.

The same pattern applies to the per-platform equivalents: Apple Business Manager device assignments derived from OrgPath, Android Zero-Touch configurations derived from OrgPath, Azure Arc resource group placements derived from OrgPath. The canonical specification holds the cross-platform intent; the per-platform projections handle the platform-specific translation.

## Dynamic group memberships from OrgPath

The fourth major UIAO contribution is generation of Microsoft Entra ID security groups and their dynamic membership rules from OrgPath. Microsoft Entra ID supports dynamic groups whose membership is determined by attribute-based rules, but the rules themselves are authored manually in the admin center and accumulate over time as a sprawling collection of overlapping definitions.

With UIAO, dynamic groups are generated from OrgPath classifications. A canonical specification expresses "the group of devices currently in business units handling controlled unclassified information with security tier high or restricted" and UIAO generates the corresponding dynamic group rule. The rule is maintained automatically as OrgPath classifications change. The organization can have many such groups — typically one per significant policy targeting boundary — without humans hand-maintaining each rule.

The benefit is twofold: the groups are guaranteed to remain consistent with the canonical specification (drift between intent and actual membership is impossible because the membership is generated), and the auditability is high (the relationship between any group and its underlying canonical specification is explicit and queryable).

## Conditional Access scope generation

The fifth major UIAO contribution is generation of Conditional Access policy scope from OrgPath. The conditional-access-rollout-playbook artifact in this kit describes the without-UIAO discipline for staged rollout of Conditional Access. With UIAO, the policy scoping for each rollout cohort is derived from OrgPath rather than from ad-hoc security group definitions. A policy targets "devices owned by employees in business units handling controlled unclassified information, in migration cohort 2 or later, in security tier high," and the security group that Conditional Access actually consumes is generated from the OrgPath classification.

Staged rollout becomes mechanically tractable: the cohort assignment is generated from canonical specification, the policy is enabled in report-only mode for that cohort, sign-in logs are reviewed for unexpected impact, and the policy moves to enforce mode after the canonical readiness criteria are met. Subsequent cohorts are added by amending the canonical specification, with the corresponding group membership updating automatically.

## Cloud Kerberos Trust scoped by OrgPath

The sixth major UIAO contribution is OrgPath-scoped Cloud Kerberos Trust for on-premises reach-back. Microsoft Entra Kerberos (Cloud Kerberos Trust) allows pure Microsoft Entra-joined devices to obtain Kerberos tickets for on-premises resources without requiring the device to be domain-joined. Without UIAO, Cloud Kerberos Trust is either enabled globally (every Entra-joined device can request tickets for any on-premises resource) or not at all, with no fine-grained control over which devices can reach which resources.

With UIAO, the reach-back is scoped: the canonical specification associates each on-premises resource class with the OrgPath classifications authorized to reach it (file shares for the marketing department reachable from devices with OrgPath classifying them as marketing-assigned; line-of-business applications for finance reachable from devices with OrgPath classifying them as finance-assigned). The scoping is enforced through OrgPath-driven Conditional Access policies that condition resource access on device classification, with the underlying Cloud Kerberos Trust mechanism providing the Kerberos ticket issuance. The resources themselves can additionally enforce the scoping through their own access control mechanisms (file share ACLs, application-internal authorization), but the Conditional Access boundary is the principal enforcement point.

## Continuous validation against canonical specification

The seventh major UIAO contribution is continuous validation of every device against its canonical specification. The validation reads the device's current state from Microsoft Entra ID (join type, registered state, last sign-in), Microsoft Intune (compliance state, configuration profile delivery, application installation state, update posture), the assigned Conditional Access scopes, and the current evidence ledger entries for the device, and compares each dimension against the canonical specification the device was provisioned to. Divergence is flagged and routed through remediation.

The divergence sources include: compliance drift (a setting changed locally on the device or by a policy override); group membership drift (a security group was modified ad-hoc, removing or adding the device); policy drift (a Conditional Access policy or compliance policy was modified in a way that affects this device's scope); ownership drift (the user assignment changed without the device record updating, perhaps because a manual reassignment was performed without canonical specification update); and unexpected configuration changes (a Microsoft Intune configuration profile was modified outside of the canonical projection workflow, perhaps for incident response).

The continuous validation produces evidence even when no divergence is detected. Each device's evidence ledger entries demonstrate that the device was checked, that the canonical specification was version-X at the time of check, that the actual state matched the specification, and that the device was in good standing as of the validation timestamp.

## Evidence emission for federal compliance attestation

The eighth major UIAO contribution is structured evidence emission to the canonical ledger, suitable for federal compliance attestation. Each phase of the five-phase onboarding process emits evidence — Procure decision, Pre-stage confirmation, Position assignment, Provision completion, Validate outcome — and each subsequent governance event (drift detection, remediation, policy update, group membership change, compliance evaluation, Conditional Access decision, application deployment) emits additional evidence. The ledger is the audit substrate for FedRAMP, FISMA, NIST 800-53, the Department of Defense Cybersecurity Maturity Model Certification, and any other compliance regime the organization is subject to.

The evidence records include the structured metadata required for the relevant compliance regime: the timestamp, the actor (human or automated system), the canonical specification version in effect at the time, the device identifier, the user identifier where applicable, the action taken, the outcome, the contextual data necessary for retrospective analysis. Auditors query the ledger directly through a queryable interface rather than requesting ad-hoc evidence packages from administrators. The audit posture is continuous — the organization can demonstrate, at any moment, that its endpoint estate meets the regime's requirements — rather than point-in-time and assembled retrospectively.

## Microsoft Coverage Doctrine for the cloud-native estate

The ninth major UIAO contribution is the Microsoft Coverage Doctrine for the cloud-native estate (the cloud-native iteration of the doctrine, sometimes designated V2 in UIAO's canon). The doctrine catalogs what Microsoft provides in the cloud-native model — Windows Autopilot, Microsoft Intune, Conditional Access, Microsoft Entra ID Protection, Microsoft Defender for Endpoint, Microsoft Defender for Identity, and the surrounding ecosystem — and what gaps remain.

The gaps include: policy expressiveness limitations on the Configuration Service Provider surface where some legacy Group Policy settings have no clean Intune equivalent; organizational positioning gaps where Microsoft Entra ID does not provide hierarchical organizational units in the Active Directory sense; data-retention gaps where Microsoft Entra ID sign-in log retention is shorter than some compliance regimes require; continuity gaps where certain on-premises capabilities require explicit cloud reach-back (and reach-back is itself an audit subject); per-application coverage gaps where the application-internal access control does not align with Conditional Access decisions; and platform-specific gaps where the macOS, iOS/iPadOS, or Android management surfaces have different feature parity with the Windows surface.

The doctrine is the input to compensating-control planning that closes each documented gap with an UIAO-provided overlay or a documented exception. The overlay may be a UIAO-managed automation (extending evidence retention beyond Microsoft's default), a third-party product integration (a data-loss-prevention overlay where Microsoft's native capability does not meet the regime requirement), or a process-level control (a manual review cadence where automation is not feasible). The doctrine catalogs the gap, the closing control, the residual risk if any, and the canonical specification version in effect.

## Know Your Customer integration at device-user binding

The tenth major UIAO contribution is Know Your Customer integration at the device-user binding boundary. Each device-user assignment is verified against the human-resources information technology system at provisioning time and continuously thereafter. A device whose assigned user has changed employment status, whose OrgPath no longer matches the user's current position, or whose user has departed the organization without device retirement is flagged for re-assignment or device retirement.

The KYC layer addresses a characteristic risk in the full transition phase: devices that were correctly assigned at provisioning time gradually drift out of correctness as the assigned user's employment changes. Without KYC integration, the drift is invisible until specific incidents surface it (a departed employee's device is found still accessing corporate resources, perhaps months after their departure). With KYC integration, the drift is detected within hours of the underlying employment change, with the device routed through the appropriate retirement, reassignment, or remediation workflow.

## Per-platform annex governance

The eleventh major UIAO contribution is governance across the per-platform onboarding annexes. The Intune-first onboarding doctrine in `src/uiao/modernization/intune-first-onboarding/` includes platform-specific annexes for Windows Autopilot, Microsoft Surface devices, macOS via Apple Business Manager, iOS/iPadOS via Apple Business Manager, Android Enterprise Zero-Touch, Samsung Knox Mobile Enrollment, and Azure Arc-managed servers. Each annex specifies the platform-specific procurement, pre-registration, positioning, provisioning, and validation mechanics that the canonical five-phase process maps onto.

UIAO ensures consistency across the annexes: the OrgPath taxonomy, the canonical compliance specification, the evidence ledger schema, and the drift engine operate identically across all platforms; the per-platform translation (Apple Business Manager device assignment ID versus Windows Autopilot profile ID, for instance) is handled by the appropriate platform adapter. New platform support is added by authoring a new annex and a new adapter; the core governance remains unchanged.

## Procurement vendor performance scoring

The twelfth major UIAO contribution is continuous procurement vendor performance scoring. Each vendor's track record on cloud-native procurement — registration success rate, profile assignment accuracy, time from purchase order to tenant registration confirmation, accuracy of confirmation reports, frequency of failure modes (registered to wrong tenant, unassigned profile, wrong profile assigned) — is recorded in the evidence ledger and aggregated into a vendor performance score. The score drives vendor qualification status (which vendors are eligible for cloud-native procurement) and informs procurement decisions when comparable hardware is available through multiple vendors.

Vendors whose track record degrades surface as governance findings before they cause significant operational impact. Vendors whose track record is consistently strong become candidates for expanded relationships and reduced verification overhead. The procurement guide's vendor qualification questions become data-driven rather than impression-driven.

## What UIAO does not change

UIAO does not modify the behavior of Windows Autopilot, Microsoft Intune policy delivery, Microsoft Entra ID authentication, Conditional Access policy evaluation, Microsoft Defender for Endpoint, Microsoft Entra Kerberos, or any other Microsoft technology in the cloud-native stack. The device-side out-of-box experience is identical whether UIAO is present or not. The end-user experience after provisioning is identical. The administrator-facing surfaces in the Intune admin center, the Microsoft Entra admin center, and the Microsoft Defender XDR portal continue to operate exactly as Microsoft designs them.

What UIAO changes is the upstream specification and the downstream attestation. The Autopilot profile assigned to a device is generated by UIAO from the canonical OrgPath specification rather than authored by hand in the Intune console. The compliance policy applied to the device is generated by UIAO from the canonical compliance specification rather than maintained as an independent Intune-resident artifact. The dynamic group memberships that drive Conditional Access scoping are generated by UIAO from the canonical OrgPath specification rather than maintained as independent Microsoft Entra group definitions. The evidence emitted after each governance event is structured against the canonical schema and the canonical specification version in effect at the time of emission, rather than assembled from logs and screenshots after the fact.

The cloud-native mechanism remains pure Microsoft. The governance posture is what UIAO provides.

## UIAO operational and cost overlay

The UIAO operational footprint in the full transition phase is, paradoxically, smaller than in the later transition phase. The five-system reconciliation work of Phase III is largely absent in Phase IV because devices have only one identity (the Microsoft Entra ID device object) rather than two; the GPO-versus-Intune policy reconciliation is absent because Group Policy is no longer in play; the Configuration Manager workload-slider work is absent because Configuration Manager has been retired for the cloud-native population. The remaining UIAO work — canonical specification maintenance, OrgPath projection, drift detection on the cloud-native surface, evidence emission, KYC integration, per-platform adapter operation — runs on a smaller server cluster than was required for the multi-plane reconciliation of earlier phases.

The cost overlay is correspondingly modest. The substrate itself is small relative to the cloud-native infrastructure it observes; the savings from full automation of the procurement-to-production pipeline, continuous validation, and structured evidence emission substantially exceed the substrate cost. For organizations subject to federal compliance regimes where audit evidence assembly otherwise consumes significant staff time, the savings are particularly pronounced.

User experience in the full transition phase is meaningfully better than in prior phases regardless of UIAO presence, but UIAO's contribution to user experience is in the consistency of the experience. Every device that lands in a user's hands has gone through the same five-phase process, has the same governance posture, has the same compliance evaluation pipeline, and produces the same evidence trail. Helpdesk troubleshooting concentrates on the small number of failure modes characteristic of the cloud-native model rather than on the per-device idiosyncrasies that accumulate without UIAO governance.

## The terminal state

The full transition phase, governed by UIAO, is the terminal state of the modernization journey. Net-new devices flow through the five-phase canonical process from procurement through validation, with the canonical specification driving every operational decision and the evidence ledger capturing every governance event. Existing legacy and hybrid-joined devices are gradually retired through hardware refresh, with their UIAO-managed migration cohort assignments driving the retirement cadence. The on-premises infrastructure that supported prior phases is gradually retired, with the residual on-premises footprint (small Active Directory for legacy applications, file servers reachable via Cloud Kerberos Trust, certificate authorities for non-Microsoft systems) bounded and managed as a legacy footprint rather than as growing infrastructure.

The continuous audit posture, the continuous drift detection, the canonical specification as source of truth, and the structured evidence ledger are all in steady-state operation. The organization can demonstrate at any moment that its endpoint estate is governed against canonical specification, that drift is being detected and remediated within bounded latency, and that the evidence trail supporting the demonstrations is queryable on demand. The compliance posture is by-construction current rather than by-effort current.
