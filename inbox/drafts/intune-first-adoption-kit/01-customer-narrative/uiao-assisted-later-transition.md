# Phase III — Later Transition: UIAO-Assisted Detailed Reference

## How to read this document

This document is the UIAO-assisted detailed reference for the later transition phase of Windows endpoint governance — the phase characterized by Hybrid Microsoft Entra Join and Microsoft Intune co-management with Configuration Manager. It parallels the structure of the without-UIAO companion ([`without-uiao-later-transition.md`](without-uiao-later-transition.md)) and describes, section by section, how the organization's internal UIAO governance framework reduces the operational cost and risk of running two device-management planes in parallel.

The later transition phase is, by the without-UIAO companion's account, the operationally most expensive phase of the modernization journey. The cost is intrinsic to running both an on-premises and a cloud device-management plane simultaneously, with the human work of reconciling between them dominating the engineering effort. UIAO's role in this phase is to make the reconciliation tractable: to detect divergence between the planes early, to canonicalize device identity across the five systems where it can appear, and to drive co-management workload assignment from a canonical policy specification rather than from ad-hoc collection membership maintained by humans.

## What UIAO is

UIAO is the organization's internal governance substrate for identity, device, and access control, sitting across Microsoft Entra ID, Microsoft Intune, on-premises Active Directory, Microsoft Configuration Manager, and human-resources information technology systems. It provides canonical organizational positioning (OrgPath) for users and devices, continuous drift detection across all the relevant surfaces, and evidence emission for compliance attestation. In the later transition phase, UIAO is most architecturally significant because the two operating planes have the most surface area to drift apart from each other and the most cross-plane reconciliation work to perform.

UIAO does not perform hybrid join itself, does not enroll devices into Microsoft Intune, and does not adjust co-management workload sliders. It observes, specifies, reconciles, and emits evidence. The underlying Microsoft technology — Active Directory, Group Policy, Configuration Manager, Microsoft Entra ID, Microsoft Intune, Microsoft Entra Connect, the hybrid join handshake mechanism — operates unchanged.

## The later transition phase reviewed

The without-UIAO companion describes the later transition architecture in detail. Devices in this phase are joined to on-premises Active Directory (a computer object exists in the directory) and additionally hybrid-joined to Microsoft Entra ID (a device object exists in the cloud directory, linked to the on-premises computer object through Microsoft Entra Connect synchronization). Devices are governed by both Group Policy (legacy plane, delivered through the domain controllers) and Microsoft Intune (cloud plane, delivered through MDM enrollment). Microsoft Configuration Manager remains in service as the application catalog and as an authority for some workload domains; Microsoft Intune is authoritative for other workload domains, with the partition controlled by configurable workload sliders in Configuration Manager. Conditional Access has matured to include device-aware conditions (require compliant device, require hybrid Entra joined device). The phase is operationally expensive because both planes must be maintained in coherent agreement, and the dual identity per device must be reconciled across five distinct system records.

## How UIAO is layered onto the later transition

UIAO carries forward from the legacy and early transition phases with its existing components — canonical inventory from the legacy phase, OrgPath on user objects from the early transition, the human-resources integration providing joiner/mover/leaver events, the evidence ledger continuing to accumulate. New components address the cloud device surface: a Microsoft Intune adapter reads device, application, compliance, and policy state; an extended Microsoft Entra ID adapter reads device objects in addition to user objects; an enhanced Configuration Manager adapter reads workload assignment state and co-management posture. The canonical specification expands to include device-plane intent: the OrgPath for each device, the expected compliance state, the expected workload-by-workload management authority (Configuration Manager versus Intune), and the canonical migration cohort assignment.

The drift engine evaluates both planes per device, surfaces cross-plane disagreement, and routes findings to the appropriate plane for remediation. A finding that an Active Directory computer object exists but the corresponding Microsoft Entra ID device object is missing is routed differently from a finding that both objects exist but their OrgPath assignments disagree, which is routed differently again from a finding that the Microsoft Intune compliance state on a device does not match the canonical compliance specification.

## Device-plane OrgPath binding

The first major UIAO contribution in the later transition is device-plane OrgPath binding. As a device completes hybrid Microsoft Entra Join, UIAO projects the canonical OrgPath onto both the Active Directory computer object and the corresponding Microsoft Entra ID device object. The device-plane OrgPath is derived from the assigned user's user-plane OrgPath (established in the early transition phase) modified by device-class attributes that are independent of the user: form factor (laptop, desktop, tablet, kiosk), asset class (corporate-issued personal-use, shared kiosk, conference room device, server, lab equipment), ownership classification (corporate-owned, contractor-owned, personal-with-corporate-data), location classification (headquarters, regional office, home office, customer site), and security tier (low, medium, high, restricted).

The result is that every hybrid-joined device carries authoritative organizational positioning on both planes, available for policy scoping, compliance evaluation, conditional access scope generation, asset reporting, and incident response triage. Without UIAO, organizational positioning is implicit through Active Directory OU placement (which targets Group Policy) and ad-hoc Microsoft Entra security group membership (which targets Conditional Access and Intune policy), and the two are not guaranteed to agree.

The OrgPath projection uses Active Directory extension attributes on the computer object and Microsoft Entra ID schema extensions or custom security attributes on the device object. Microsoft Entra Connect synchronization carries the on-premises projections into the cloud directory where applicable. The canonical specification holds the OrgPath taxonomy and the derivation rules; UIAO maintains the projection continuously, updating device-plane OrgPath as user-plane OrgPath changes (the user is reassigned, the user's role changes, the user departs and is replaced) and as device-class attributes change (a device is reassigned from a laptop role to a shared kiosk, an asset is reclassified for security-tier purposes).

## Drift detection on hybrid join

The second major UIAO contribution is drift detection on the hybrid join itself. The hybrid join handshake is silent: when a device joins the on-premises domain and the scheduled "Automatic-Device-Join" task runs successfully, the device becomes hybrid-joined with no user-visible event; when the task fails, the device remains domain-joined-only with no user-visible event either. The failure is silent until the user attempts to access a Conditional Access-protected resource that requires hybrid join, at which point access is denied, often weeks or months after the underlying join failure.

UIAO's drift engine watches the hybrid join handshake for each device and surfaces failures within hours rather than during the eventual access denial. The drift signals include: devices that joined the on-premises domain but failed to register in Microsoft Entra ID (the most common failure, attributable to network reachability, Entra Connect lag on the corresponding computer object, Service Connection Point misconfiguration, time skew, or certificate issues); devices that registered in Entra ID but were never enrolled in Microsoft Intune (typically attributable to MDM scope misconfiguration or licensing gaps); devices whose hybrid identity is present but stale because the Entra Connect sync has not propagated a required attribute change; duplicate device objects in Entra ID arising from re-imaging or re-joining without proper retirement of the prior object; and devices whose Service Connection Point points at a tenant other than the intended one (which occurs when an organization has multiple tenants and the SCP was configured for the wrong one).

Each finding is attributed to its likely root cause, and remediation routing is automated where possible (retrying the registration scheduled task, retrying MDM enrollment, retiring stale duplicates) or surfaced to identity engineering where human judgment is required. The result is that silent hybrid join failures, the single most operationally consequential failure mode of the later transition phase, are converted from invisible accumulating risk into visible findings worked on a daily cadence.

## Five-system identity reconciliation

The third major UIAO contribution is reconciliation of device identity across the five systems where it can appear. A device in the later transition phase has, potentially, an Active Directory computer object (on-premises identity), a Microsoft Entra ID device object (cloud identity, linked to the on-premises through hybrid join), a Microsoft Intune managed device record (management identity, linked to the Entra device through enrollment), a Microsoft Configuration Manager client record (legacy management identity, linked to the Active Directory computer through the client agent), and a Windows Autopilot device record (provisioning identity, linked to the device's hardware hash). Each of these records can change independently, and disagreement between them is operationally common.

UIAO reconciles the five records continuously, producing one canonical device record per physical asset and emitting findings when the underlying records disagree. The reconciliation logic uses serial number as the primary key (the most stable identifier), hostname as a secondary key, hardware hash as a tertiary key for Autopilot reconciliation, and user assignment as a context check. When records disagree, the finding identifies which records exist, which are missing, which carry conflicting attributes, and what the canonical record indicates the correct state should be.

Common disagreement patterns surfaced by the reconciliation include: a device that has been re-imaged retains its old Microsoft Intune record but acquires a new Active Directory record (orphaned Intune record requires retirement); a device that was migrated between organizational units retains its old Configuration Manager collection membership (collection drift requires remediation); a device whose Microsoft Entra ID device object was manually deleted continues to authenticate via its Active Directory machine credential and Configuration Manager client (the cloud-side de-registration was incomplete); and a device that exists in Autopilot but never completed onboarding has the Autopilot record without any subsequent record (procurement-to-production pipeline failure, addressable via the procurement-handoff workflow).

The reconciliation work, in the absence of UIAO, is performed manually by engineers writing ad-hoc PowerShell scripts that query the five systems separately and join the results by serial number — work that consumes engineering hours per incident and that is performed only reactively. With UIAO, the work is continuous and automated, with engineers consuming the resulting findings rather than performing the discovery.

## Co-management workload assignment from canonical policy

The fourth major UIAO contribution is co-management workload assignment driven by canonical policy specification. Microsoft Configuration Manager exposes workload sliders that partition device-management responsibility between Configuration Manager and Microsoft Intune across configurable workload domains (compliance policies, resource access policies, device configuration, Windows Update policies, Endpoint Protection, client applications, Office Click-to-Run apps, Microsoft Defender for Endpoint integration). The slider for each workload can be set to Configuration Manager, Pilot Intune (a designated pilot collection receives the workload from Intune while the rest remains on Configuration Manager), or Intune.

Without UIAO, workload assignment is driven by Configuration Manager collection membership rules maintained by humans, and the assignment drifts over time as collections are modified ad-hoc. With UIAO, workload assignment is expressed against OrgPath ("devices in regulated business units with migration cohort assignment 3 and security tier high should have the compliance, configuration, and update workloads on Microsoft Intune as of this date; the application workload remains on Configuration Manager pending the application catalog migration project") and Configuration Manager collection membership is generated from the canonical specification. The collections are no longer maintained by humans editing query syntax; they are projected from the specification and updated automatically as OrgPath assignments change or as the specification is amended.

This pattern reduces the operational cost of co-management substantially. The decision of which devices should have which workload on which plane is made at the canonical specification level, by architects with full context, and the implementation propagates automatically. Drift between expected and actual workload assignment surfaces as a finding rather than going undetected until a specific device exhibits unexpected behavior.

## Migration risk scoring

The fifth major UIAO contribution is migration risk scoring per device. The migration from the later transition phase toward the full transition phase (or, for existing devices, toward retirement through hardware refresh) requires a per-device assessment of readiness: which devices can be migrated immediately, which require remediation first, and which should be retired rather than migrated. The assessment depends on multiple factors that vary independently.

UIAO computes a risk score per device that estimates the likelihood of a clean migration. The score considers: Trusted Platform Module health (present, version 2.0, attestable, not cleared); BitLocker recovery key presence and escrow location; Windows version and feature update history; hardware model compatibility with the target operating model (Autopilot support, supported drivers, supported feature set); peripheral and driver compatibility; network connectivity classification (devices in restrictive networks may fail Autopilot's network requirements); user training and readiness; and any open drift findings on the device. The score is a structured value (typically a low-medium-high categorization with detailed contributing factors), not an opaque number.

The score drives migration cohort assignment continuously. Devices that meet all readiness criteria join cohort 1 (immediate-migration candidates). Devices that require modest remediation join cohort 2 (queued for remediation, then migration). Devices that require substantial remediation join cohort 3 (longer remediation, potentially deferred until hardware refresh). Devices that should be retired rather than migrated join cohort 4 (hardware refresh queue). The cohort assignment is recomputed continuously as remediations land, as new findings arise, and as canonical specification changes (perhaps the readiness threshold tightens or loosens).

Migration planning consumes the cohort assignments as input. Rather than humans surveying the estate device-by-device, the migration plan is generated from the canonical inventory and the risk scoring; the humans concentrate on the canonical specification (what makes a device ready, what migration cadence is acceptable, what remediation paths are available) and on exceptions (devices that the scoring engine cannot classify confidently).

## Compliance policy generation from canonical specification

The sixth major UIAO contribution is generation of Microsoft Intune compliance policies from the canonical compliance specification. A compliance policy in Microsoft Intune evaluates whether a device meets a defined set of criteria (Windows version, BitLocker state, Microsoft Defender Antivirus state, password policy, Trusted Platform Module presence, and others), with the result fed into Conditional Access as a device-aware condition. The policy is authored in the Intune admin center and assigned to security groups.

UIAO holds the canonical compliance specification and projects it into Microsoft Intune as concrete compliance policies. The specification expresses intent ("devices with security tier high should require BitLocker, Trusted Platform Module 2.0, current operating system feature update minus zero or one, current Microsoft Defender Antivirus signatures with maximum age of seven days, and Microsoft Defender for Endpoint risk score of low or none"), and the projection generates the corresponding Intune compliance policies and assigns them to security groups derived from OrgPath. Specification changes flow through automatically; the policies in the Intune admin center are not maintained by humans editing the compliance policy directly.

The benefit is consistency between the compliance specification and the compliance policy in production. Without UIAO, the two are independent artifacts maintained by potentially different humans, and they drift apart over time as specification changes are made without policy updates, or vice versa.

## Evidence emission per workload transition

The seventh major UIAO contribution is evidence emission per workload transition. Each time a co-management workload slider moves a workload domain from Configuration Manager to Microsoft Intune for a population of devices, UIAO records the transition in the evidence ledger: which workload, which devices (with their canonical OrgPath classifications), which canonical policy version was active at the moment of transition, which administrator authorized the transition, what compliance state the affected devices had at the moment of transition, and what the post-transition state is.

The evidence is the audit record of how the estate moved from co-management toward Intune-only management. It supports retrospective compliance attestation (demonstrating that the workload transitions were authorized, documented, and produced the intended state). It supports root-cause analysis when something goes wrong after a transition (the canonical record of what changed when becomes the input to incident investigation). It supports migration planning (a transition that produced unexpected drift becomes input to the planning of the next transition).

## Stale hybrid record cleanup

The eighth major UIAO contribution is automated cleanup of stale hybrid device records. The later transition phase accumulates stale records at all five system levels: Active Directory computer objects for retired hardware, Microsoft Entra ID device objects for devices that have been retired or re-imaged, Microsoft Intune managed device records for devices that no longer exist, Configuration Manager client records for devices that have not reported in extended periods, and Microsoft Autopilot records for devices that were registered but never completed onboarding.

UIAO's stale-object identification, extended from the legacy phase to cover all five surfaces, continuously identifies records that should be retired and routes them through retirement workflows. The workflows are configurable per surface: Active Directory objects may go through disable-then-delete with retention windows, Entra ID device objects may be deleted immediately after canonical confirmation of retirement, Intune records may be retired through the Intune admin center's retirement workflow, and so on. The accumulated cleanup across the five surfaces is substantial; estates that have been operating in Phase III for a year or more typically reduce their stale record counts by half or more within months of UIAO's deployment to the hybrid surface.

## Cross-plane policy reconciliation

The ninth major UIAO contribution is reconciliation between Group Policy and Microsoft Intune policy for any setting present in both. The later transition phase exposes a characteristic operational hazard: both Group Policy and Microsoft Intune can express the same configuration setting (a security-baseline setting, an Internet Explorer Mode setting, a BitLocker setting, a Microsoft Defender setting, an updates setting), and the resulting behavior on a device depends on which mechanism last wrote to the underlying registry location. The dependency is invisible to administrators inspecting either tool individually; it emerges only in operational behavior on the device.

UIAO catalogs the settings present in both Group Policy and Microsoft Intune for each device population, projects the canonical policy specification as the source of truth, and surfaces drift when the projection from canonical-to-Group-Policy and canonical-to-Intune produces different applied values. The reconciliation work, which would otherwise be performed by engineers debugging specific incidents, is converted into a continuous finding workflow.

## What UIAO does not change

UIAO does not perform hybrid Microsoft Entra Join, does not modify the Microsoft Entra Connect synchronization engine, does not modify the Group Policy delivery mechanism that triggers hybrid registration, does not modify the certificate trust relationship between the on-premises domain and Microsoft Entra ID, does not enroll devices into Microsoft Intune, does not adjust the workload sliders in Microsoft Configuration Manager directly, and does not modify the underlying Conditional Access evaluation engine. Each of these mechanics remains pure Microsoft technology, operating exactly as it would in a non-UIAO environment.

What UIAO changes is the cost and risk profile of running two management planes in parallel. The work that humans would otherwise do — reconciling identity across five systems, discovering silent join failures, planning migration cohorts, generating audit evidence, projecting canonical policy intent into Configuration Manager collection membership and Microsoft Intune policy assignments — is performed continuously by UIAO. The phase remains operationally expensive (two planes are inherently more expensive than one), but the marginal cost of governance, audit, and migration planning is substantially reduced.

## UIAO operational and cost overlay

The UIAO operational footprint in the later transition phase grows significantly compared to the early transition, reflecting the addition of device-plane adapters (Microsoft Intune, extended Microsoft Entra ID, enhanced Configuration Manager) and the substantial expansion of canonical specification to cover device-plane intent, compliance specifications, workload assignments, and migration cohort criteria. The substrate continues to run on a small server cluster (UIAO itself does not require large infrastructure regardless of the size of the estate it observes), but the canonical specification expands substantially as the device-plane governance comes online.

The cost of UIAO in this phase is significantly offset by the cost it avoids. The later transition phase without UIAO carries substantial hidden costs: silent hybrid join failures producing user-facing incidents that consume helpdesk and engineering time; estate surveys for migration planning consuming engineering weeks per planning cycle; reconciliation work between the five identity systems consuming engineering days per incident; manual maintenance of Configuration Manager collection membership consuming administrator hours per week; audit evidence assembly consuming engineering and compliance staff time per audit window. UIAO converts most of these costs from human labor into substrate operation, with corresponding reduction in incident frequency and staffing requirements.

The total cost of the modernization effort is largely determined by the duration of Phase III. UIAO reduces the duration by making the work of migrating workloads, retiring legacy devices, and onboarding cloud-native devices substantially more tractable.

## Carry-forward to subsequent phases

The investment in UIAO during the later transition phase is the most valuable point of intervention in the entire modernization journey, because the substrate established here carries forward directly into Phase IV (the full transition). The device-plane OrgPath established here becomes the OrgPath that drives Autopilot pre-registration in Phase IV. The migration risk scoring continues to operate in Phase IV, assessing devices that should be migrated from Phase III to Phase IV (existing hybrid-joined devices being retired and replaced) and assessing the procurement-to-production readiness of net-new devices. The compliance policy specification continues to project into Microsoft Intune, with the projection becoming the only policy plane (Configuration Manager is retired for Phase IV devices). The evidence ledger continues to accumulate, producing continuous audit substrate spanning the entire journey.
