# Phase IV — Full Transition: Step-by-Step Laptop Onboarding (UIAO-Assisted)

## Audience and purpose

This guide is for new IT staff learning the cloud-native laptop onboarding process in an environment where UIAO governance is in place. The mechanics from the user's perspective (unboxing, power-on, network connection, sign-in, Enrollment Status Page, desktop) are identical to the without-UIAO version. What changes is the upstream pipeline that produces the device's Autopilot pre-registration, the configuration profiles and policies it receives, the dynamic group memberships it acquires, and the validation that confirms it reached canonical state. The result is that Phase IV under UIAO operates as a fully governed assembly line: from purchase-order issuance through the user's first sign-in to ready-to-work desktop, every step is specified, automated, and recorded against the canonical specification.

Read [`without-uiao-full-transition.md`](without-uiao-full-transition.md) for the underlying user-facing procedure, then read this document for the UIAO five-phase canonical process that surrounds it.

The phase architecture under UIAO is described in [`01-customer-narrative/uiao-assisted-full-transition.md`](../01-customer-narrative/uiao-assisted-full-transition.md), and the canonical doctrine is anchored at ADR-067 (Intune-first asset onboarding) and ADR-071 (canonical five-phase process specification) in the organization's internal repository.

## The five-phase canonical process

UIAO formalizes Phase IV onboarding as a five-phase sequence anchored in ADR-067 and ADR-071. Each phase has specified inputs, outputs, evidence emissions, and exit criteria.

**Procure**: The procurement decision captures the OrgPath assignment for the device — business unit, region, asset class, ownership classification, security tier, cost center, assigned user (if known at purchase order time). The canonical device record is created at PO issuance with OrgPath in place. The procurement-side metadata (vendor, model, configuration, warranty terms) is recorded alongside the governance-side metadata. The PO itself includes the contract language requiring vendor pre-registration with the deployment profile derived from OrgPath.

**Pre-stage**: The vendor captures the device's hardware identifiers at order fulfillment (hardware hash for Windows Autopilot, serial number for Apple devices in Apple Business Manager, IMEI for Android in Zero-Touch, onboarding token for Azure Arc-managed servers). The vendor uploads the identifiers to the organization's tenant via the appropriate API (Cloud Solution Provider API for Autopilot, Apple Business Manager API for Apple devices, etc.). UIAO verifies the registration automatically through the relevant API by querying for the expected serial number; the verification fires as a finding if absent. The deployment profile, generated from the OrgPath, is assigned to the device record.

**Position**: With the device pre-registered and the profile assigned, UIAO sets up the device's operational position in the cloud directory and management surfaces. The dynamic Microsoft Entra security groups that will contain the device are generated from OrgPath classifications. The Conditional Access scope that the device will fall under is generated from OrgPath. The Microsoft Intune compliance policy that will evaluate the device is generated from the canonical compliance specification for the device's OrgPath. The Microsoft Intune configuration profiles that will apply are generated from the canonical configuration specification. The application set that will be delivered (required Win32 apps, Microsoft 365 Apps, optional apps in the Company Portal) is generated from OrgPath role assignments. The Windows Update for Business ring assignment is derived from OrgPath migration cohort. All of this happens server-side, before the user receives the device.

**Provision**: The user receives the device, powers it on, connects to the network, and signs in. The Autopilot experience runs as described in the without-UIAO version, with the device joining Microsoft Entra ID, enrolling in Microsoft Intune, and applying the configuration that was set up in the Position phase. The user reaches the desktop ready to work. The user-facing experience is identical to the without-UIAO version because the underlying Microsoft mechanism is identical.

**Validate**: After provisioning completes, UIAO verifies that the deployed device matches its canonical specification end-to-end. The Microsoft Entra ID device object has the expected OrgPath. The Microsoft Intune managed device record has the expected compliance state. The assigned groups, Conditional Access scopes, configuration profiles, and applications are in the expected state. The device has emitted the expected evidence to the ledger. Successful validation admits the device to active operation. Failed validation routes the device through a remediation workflow with the specific gap identified.

## Software inventory at provisioning completion

Identical to the without-UIAO version. UIAO does not add a device-side agent; the substrate operates server-side, reading from the Microsoft cloud management surfaces.

## Phase 1 — Procure (UIAO-driven)

The procurement workflow under UIAO is significantly more structured than the without-UIAO version.

1. **Requisition arrives in procurement**: The requesting business unit (or the human-resources joiner event for new hires) submits a hardware requisition. The requisition includes the requesting user (or the role being onboarded), the business justification, and the hardware class request.

2. **OrgPath assignment**: UIAO computes the canonical OrgPath for the future device from the requisition data combined with the requesting user's user-plane OrgPath. The OrgPath classification determines: which device class is appropriate (executive, standard knowledge worker, kiosk, lab, etc.), which deployment profile applies, which compliance specification governs, which application set is appropriate, which security tier the device will operate in.

3. **Canonical device record created**: UIAO creates the canonical device record with the OrgPath assignment in place, status "On order — not yet pre-staged." The record is referenced throughout the rest of the workflow.

4. **PO with embedded contract language**: The procurement officer issues the PO with the vendor pre-registration clause embedded (see [`02-coworker-artifacts/procurement-one-pager.md`](../02-coworker-artifacts/procurement-one-pager.md)). The PO references the Autopilot deployment profile by identifier — the profile is generated by UIAO from the OrgPath and given an identifier that the vendor uses to associate the device with the correct configuration at fulfillment.

5. **Evidence emission**: UIAO emits an evidence record to the canonical ledger marking the procurement decision: OrgPath assigned, PO issued, vendor identified, expected delivery date, canonical device record identifier.

Time: minutes per requisition, with batch processing for multi-device orders. The procurement officer's hands-on time is essentially unchanged from a pre-UIAO procurement workflow; what changes is the structured upstream specification that the workflow produces.

## Phase 2 — Pre-stage (vendor-driven, UIAO-verified)

1. **Vendor fulfillment**: The vendor receives the PO, builds the device to specification, and captures the hardware hash during the fulfillment step. The hash capture is part of the vendor's standard cloud-native procurement workflow — vendors offering Autopilot pre-registration have integrated this into their order-fulfillment pipeline.

2. **Vendor uploads to tenant**: The vendor uses the Cloud Solution Provider Autopilot API (or the manual upload via the Microsoft Intune admin center for vendors without API integration) to register the device hash to the organization's tenant. The device record is created in Microsoft Entra ID's Autopilot device list.

3. **Profile assignment**: The vendor assigns the Autopilot deployment profile specified in the PO. Alternatively, UIAO observes the new Autopilot device record and assigns the profile automatically based on the device's OrgPath (which UIAO knows from the canonical record).

4. **UIAO verification**: UIAO's Autopilot adapter polls the Microsoft Intune service for the expected device record. Detection of the record triggers an evidence ledger entry and updates the canonical device record's status to "Pre-staged — ready for ship." Absence of the expected record at the expected time triggers a finding routed to procurement: "Vendor has not registered device [serial number] expected from PO [number] within [window]; verify with vendor."

5. **Vendor performance scoring**: UIAO records the registration outcome (success, failure, time-to-registration) against the vendor's performance score. Vendors whose track record degrades surface as findings before they affect significant device volume.

The vendor's hands-on work is identical whether UIAO is in place or not. What changes is the verification and accountability around the vendor's work.

## Phase 3 — Position (UIAO-driven, server-side)

This phase happens entirely server-side, before the device ships, while the device is still at the vendor or in transit. The user never sees this phase directly.

1. **Microsoft Entra security group memberships**: UIAO generates the device's dynamic security group memberships from the OrgPath. The groups drive: Conditional Access scoping, configuration profile assignment, application deployment assignment, update ring assignment, compliance policy assignment.

2. **Conditional Access scope verification**: UIAO confirms the device, once active, will fall under the appropriate Conditional Access policies based on its group memberships. The "What If" tool in Microsoft Entra is queried by UIAO to verify the expected access decisions.

3. **Configuration profile assignment**: The configuration profiles relevant to the device's OrgPath (security baseline, BitLocker policy, Windows Hello for Business policy, Wi-Fi profile, VPN profile if applicable, certificate profile if SCEP/PKCS is in use) are assigned to the group containing the device. UIAO confirms each profile is in the expected state.

4. **Compliance policy projection**: UIAO projects the canonical compliance specification for the device's OrgPath into a Microsoft Intune compliance policy and assigns it to the device's group. The compliance criteria reflect the OrgPath security tier (a high-tier device has stricter compliance criteria than a medium-tier device).

5. **Application assignment**: The required Win32 apps, Microsoft 365 Apps, optional Win32 apps in the Company Portal, and Microsoft Store apps are assigned to the device's group. The assignment is generated from OrgPath role and the canonical application catalog.

6. **Windows Update ring assignment**: The device's update ring (Pilot, Broad, Slow) is assigned based on OrgPath migration cohort.

7. **Evidence emission**: UIAO emits evidence records for each positioning action, producing the audit trail showing how the device was prepared for the user's first sign-in.

By the end of the Position phase, the device record in the cloud is configured to deliver exactly the configuration the canonical specification calls for. The Provision phase merely executes what Position has prepared.

## Phase 4 — Provision (user-facing, identical to without-UIAO)

The Provision phase is the user's first-boot experience, identical to the without-UIAO version: unbox, power on, connect to network, sign in to Entra ID, Autopilot detects pre-registration, ESP runs, configuration applies, desktop reached. The user's experience is unchanged because the underlying mechanism is unchanged. What is different is that the configuration that applies was generated upstream by UIAO from the canonical specification, so the device emerges from ESP in the canonically-correct state by construction.

The user's role in Provision is identical to the without-UIAO version. The user does not interact with UIAO. The welcome packet referencing UIAO concepts is internal-facing and does not appear in user-facing documentation.

## Phase 5 — Validate (UIAO-driven, server-side)

After ESP completes and the user reaches the desktop, UIAO performs the validation that confirms canonical state.

1. **Microsoft Entra ID device object validation**: UIAO queries Microsoft Entra for the device, confirms the join type is "Microsoft Entra joined," confirms OrgPath is projected onto the device object, confirms the device is in the expected security groups, confirms the device is associated with the expected primary user.

2. **Microsoft Intune managed device validation**: UIAO queries Microsoft Intune for the device, confirms the managed device record exists, confirms the assigned configuration profiles are in "Succeeded" state, confirms the compliance policy is in "Compliant" state, confirms the required Win32 apps are in "Installed" state, confirms the Microsoft 365 Apps are activated.

3. **Microsoft Defender for Endpoint validation**: UIAO confirms the device is onboarded to Microsoft Defender for Endpoint and is reporting telemetry. The initial risk score is recorded.

4. **Conditional Access validation**: UIAO confirms the device, on its first sign-in, was admitted by Conditional Access (the policies that should have evaluated did, and produced the expected grant).

5. **Evidence chain completeness**: UIAO confirms the evidence ledger has entries for every step from Procure through Validate. Any missing entry surfaces as a finding requiring investigation.

6. **Canonical state confirmation**: UIAO confirms the device record's canonical state matches the procurement-time specification end-to-end. The canonical record's status transitions from "Provisioned — awaiting validation" to "Validated — active operation."

If Validate finds gaps, the device is not yet admitted to active operation. The technician (helpdesk or endpoint management) investigates the specific gap and resolves it. Common causes: an ESP step that completed with a transient error (resolved by Intune sync), a Conditional Access policy that did not evaluate as expected (resolved by re-checking the policy scope), a compliance policy that flipped to non-compliant for a transient reason (resolved by waiting for the next evaluation cycle).

When Validate completes successfully, the device is in canonical state and continuous monitoring begins.

## Continuous monitoring after validation

UIAO continues monitoring the device for the duration of its operational life. The monitoring covers: ongoing compliance state (drift to non-compliant surfaces as a finding); configuration profile application state (a profile that has flipped to "Error" or "Conflict" surfaces); application installation state (a required app that has uninstalled surfaces); device sign-in activity (an unexpected sign-in pattern surfaces); Microsoft Defender for Endpoint risk score (a risk elevation surfaces); group membership consistency (a device that has been removed from an expected group surfaces); KYC continuity for the device-user binding (a user employment state change surfaces with the device assignment).

Findings route to the operational queue with the canonical specification context. The user typically does not interact with IT for routine matters; the helpdesk involvement is concentrated on legitimate exception handling rather than routine break-fix work.

## Tools and equipment required

Same as without-UIAO: cloud admin consoles (Microsoft Intune, Microsoft Entra, Microsoft Defender XDR), optionally a barcode scanner for the IT-receiving fallback path. UIAO adds access to the UIAO console (typically web-browser-accessible) for canonical specification management, finding queue review, and evidence ledger querying. The console operations are typically performed by engineering and architecture staff rather than by deployment technicians; the deployment technician's tools are largely unchanged.

## Common failures during the five-phase process

Each phase has characteristic failure modes that UIAO surfaces directly.

**Procure failures**: OrgPath cannot be computed because the requesting user's user-plane OrgPath is incomplete (KYC finding from earlier); the PO is issued with the wrong profile identifier because the canonical specification was not consulted (process drift, surfaces as a finding); the vendor is not qualified for cloud-native procurement (vendor performance score below threshold).

**Pre-stage failures**: The vendor does not register the device within the expected window (finding routed to procurement for vendor follow-up); the vendor registers to the wrong tenant (finding requires cross-tenant remediation); the vendor registers but does not assign the profile (finding triggers UIAO-automated profile assignment).

**Position failures**: A canonical specification has changed in a way that affects an in-flight device's expected configuration (finding triggers re-projection of the affected policies); a dependency on user-plane OrgPath is missing (the user's OrgPath has drifted, KYC finding takes precedence).

**Provision failures**: All of the without-UIAO failure modes apply (ESP errors, Conditional Access denial, MFA issues, network connectivity issues). UIAO does not change the mechanics but does not introduce additional failure modes either.

**Validate failures**: Profile applications in "Error" or "Conflict" state at validation time (finding identifies the specific profile and surfaces the canonical-specification value that should apply); compliance policy stuck "Not evaluated" (finding triggers a sync and re-evaluation); evidence chain gaps (finding identifies the missing emission point and triggers investigation of the relevant adapter).

The class of failure that survives into production under UIAO Phase IV is much narrower than under the without-UIAO version. Most failure modes are detected at Validate before the user encounters them.

## Total time and resource cost per device

Provisioning time per device: same as without-UIAO (15 to 60 minutes elapsed for the user's first boot).

Hands-on IT staff time per device: typically 2 to 5 minutes. The pre-shipment verification, the post-provisioning admin-console verification, and the Validate confirmation are all automated under UIAO; staff intervention is concentrated on exception handling.

The substantial UIAO cost savings in Phase IV are at the operational-overhead level rather than at the per-device level. The Validate phase catches most failures before they reach the user, dramatically reducing helpdesk volume. The continuous evidence emission produces audit substrate without manual assembly. The canonical specification drives every operational decision, eliminating the drift between intent and implementation that characterizes the without-UIAO version.

For organizations subject to federal compliance regimes (FedRAMP, FISMA, NIST 800-53), the audit-evidence cost reduction alone typically justifies the UIAO investment in Phase IV. Audits that previously consumed engineering and compliance staff time for weeks per audit window become routine queries against the evidence ledger.

## The terminal state under UIAO

Phase IV under UIAO is the terminal state of the modernization journey: net-new devices flow through the five-phase canonical process from procurement through validation; the canonical specification drives every operational decision; the evidence ledger captures every governance event; continuous validation confirms canonical state; continuous drift detection surfaces deviations within hours of occurrence. The organization can demonstrate at any moment that its endpoint estate is governed against canonical specification, that drift is being detected and remediated within bounded latency, and that the evidence trail supporting the demonstrations is queryable on demand. The compliance posture is current by construction rather than current by effort.

This is the architectural endpoint that the journey from Phase I through Phase IV has been building toward, and the operational steady-state that UIAO governance maintains.
