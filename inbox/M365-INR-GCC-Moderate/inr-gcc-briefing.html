Technical briefing Network & compliance Revised 2026-09-10

Informed Network Routing is not available to GCC Moderate

A corrected assessment: what Microsoft actually documents, what FedRAMP 20x does and does not change, and what to deploy on Catalyst SD-WAN instead.

Bottom line

Microsoft 365 Informed Network Routing (INR) cannot be enabled in a GCC Moderate tenant. This is a Microsoft product-availability limitation, stated plainly in Microsoft's own documentation. It is not a consequence of FedRAMP boundary rules, and FedRAMP 20x does not change it.

The earlier framing — that legacy FedRAMP boundary scoping blocked INR and that the Consolidated Rules for 2026 removed that barrier, leaving only Microsoft engineering — asserts a cause that no public source establishes. The limitation is real; the explanation was not evidenced. This revision replaces it with what is documented.

Section 1 — What the primary source says

The limitation, in Microsoft's words

“Microsoft 365 informed network routing supports tenants in WW Commercial cloud but not the GCC Moderate, GCC High, DoD, Germany, or China clouds.”
Microsoft Learn — Microsoft 365 informed network routing, Overview

This single sentence is the authoritative citation for the whole question. Any briefing that reaches an Authorizing Official or a customer should carry it in place of secondary commentary. Three further facts from the same article bound the discussion:

Documented

The channel is bi-directional and carries circuit-level operational data

Microsoft periodically returns application-experience feedback per office location and Internet circuit; the SD-WAN solution periodically returns “network-level optics data, including configuration information and usage statistics associated with the device and attached circuits.” Microsoft states no personal information is collected and that data is aggregated to office locations and circuits.

Source: Microsoft Learn, Overview
Documented

Circuits are identified by public egress IP, configured per location

INR “identifies traffic associated with a specific office location and Internet circuit based on the public IP address used to send network traffic to Microsoft.” Administrators enumerate each location's egress IP ranges in the admin center. Microsoft also notes INR “might not provide significant value” at a branch with no direct Internet access circuit.

Source: Microsoft Learn, Requirements & Configuring
Documented

Exchanged data is stored in customer-selected Azure regions, outside the tenant

Data exchanged between Microsoft and the SD-WAN provider is held in a storage location chosen at enablement, described as “geographical areas containing Microsoft Azure regions,” retained up to 30 days. Microsoft explicitly notes the SD-WAN solution's own location “might not be within the same region” and directs customers to evaluate data storage location requirements with the vendor before production deployment.

Source: Microsoft Learn, Data storage
Section 2 — Why, and how confident we are

The likely reason, graded honestly

Microsoft publishes the limitation without publishing a reason. The strongest available explanation is architectural and sits in the data-storage paragraph above, not in FedRAMP scoping.

Inferred

The feature's data plane terminates outside the government cloud

INR's exchanged data rests in commercial Azure regions and is then handed to a third-party SaaS operator whose location may differ. A government-cloud service description that commits to US-sovereign storage and screened-personnel operations cannot absorb that path without a separate government-side data plane and a separate vendor arrangement. That is a substantial engineering and contractual build, not a toggle — which is a sufficient explanation for non-availability across all five restricted clouds, including Germany and China, where US FedRAMP rules are irrelevant.

Basis: Microsoft Learn data-storage terms + the scope of the exclusion list. Microsoft has not confirmed this rationale.
Unsupported

That Microsoft or agency AOs judged INR telemetry an unacceptable attack surface

No Microsoft, FedRAMP, or agency source states this. It is a plausible hypothesis about sensitivity — circuit performance and per-site usage statistics do describe branch topology — but presenting it as the operative reason is speculation. Note also that it does not survive contact with the recommended alternatives: ThousandEyes agents stream comparable path telemetry to a third-party SaaS. The distinction between INR and ThousandEyes is authorization status, not attack surface.

No source located supporting a stated security rationale.
Unsupported

That FedRAMP boundary rules ever blocked INR

FedRAMP boundary and scoping rules govern which information resources a cloud service provider must include in its own assessment. They do not govern which features Microsoft ships to a sovereign cloud, and they do not reach the agency's Catalyst SD-WAN Manager, which is customer-operated infrastructure and not a cloud service offering under assessment. No source ties INR's GCC unavailability to boundary scoping in either direction.

Claim withdrawn from the prior version.
Section 3 — The FedRAMP position, corrected

What the Consolidated Rules for 2026 actually change

The Minimum Assessment Scope is real and it is a genuine liberalization — but it liberalizes the wrong dimension for this question, and it is not yet the operative regime for Microsoft's existing GCC certification.

Correction — Rev 5 characterization

Rigid perimeter; all connected APIs in-scope must inherit authorization. Strict interconnection security agreements required.

Rev 5 already permitted external and non-FedRAMP services with documented risk, via the Control Implementation Summary, the Customer Responsibility Matrix, interconnection agreements, and the external services inventory. Describing it as “all-or-nothing” overstates the prior state to make the change look larger than it is — a FedRAMP-literate reader will discount the rest of the document on that basis.

Correction — direction of the metadata argument

MAS requires providers to assess “all information resources that are likely to handle federal customer data or likely to impact the confidentiality, integrity, or availability of federal customer data,” and states that resources outside that test — “including most metadata” — should be excluded from FedRAMP assessment. This cuts against the original thesis rather than for it: if telemetry metadata falls outside assessment scope, then boundary rules were never the obstacle standing between GCC Moderate and INR, under either ruleset.

Correction — timeline and applicability

FedRAMP 20x is the operative regime; compliance now permits it.

CR26 was finalized 2026-06-25 and took effect 2026-07-04, but enforcement for most rulesets begins 2027-01-01, and existing Rev 5 certifications remain active into 2028. Office 365 GCC operates today largely under Rev 5. “Compliance already allows it, only Microsoft blocks it” is premature even on its own terms.

2026-06-25 CR26 finalized
2026-07-04 Effective; early adoption for Rev 5 holders
2027-01-01 Enforcement of most rulesets begins
2027-06-11 No new Rev 5 applications accepted
2028-12-31 Planned Rev 5 sunset

One terminology note for mixed audiences: CR26 uses Minimum Assessment Scope, while the earlier 20x Phase One document was renamed Minimum Assessment Standard to avoid confusion with the scope of FedRAMP under M-24-15. Both abbreviate to MAS. Spell it out on first use.

Section 5 — What to deploy instead

Native optimization paths on Catalyst SD-WAN

Each of these is available today in a GCC Moderate context. The first item corrects a link error in the prior version that would misconfigure a production fabric.

Endpoint-driven steering via the M365 IP & URL web service

Corrected

Ingest the endpoint feed through Cloud OnRamp for SaaS / SD-AVC so Optimize-category traffic egresses locally via DIA.

There is no GCC instance. The web service accepts Instance=Worldwide, China, USGovDoD, or USGovGCCHigh only, and GCC Moderate is served by Worldwide — the page is titled “Microsoft 365 Worldwide (+GCC).” The prior version linked the DoD endpoints page; a fabric configured from that feed would classify the wrong prefixes and break M365 optimization.

Synthetic HTTP/HTTPS probing in Cloud OnRamp for SaaS

Probe Microsoft front-end endpoints from each site and select paths on measured loss, latency and jitter rather than on a vendor-supplied quality signal. This is the direct functional substitute for INR's feedback loop, and it keeps all measurement inside the agency's own fabric.

Probing measures the path to a front door, not application experience inside the service — the gap INR was built to close. In a commercial tenant, Cloud OnRamp blends INR's opinion score into this same best-path algorithm; in GCC that input is simply absent, so this is the algorithm running one input short rather than an equivalent alternative. Configuration in Section 6.

Cisco ThousandEyes for Government

FedRAMP Moderate authorized

Independent path and application monitoring with a federal authorization of its own, listed on the FedRAMP Marketplace. Use it for circuit degradation attribution and hop-by-hop evidence during incidents. Deployment in Section 7.

State this precisely: the authorization belongs to the ThousandEyes for Government platform. Enterprise Agents are customer-deployed software that report into it; agents do not hold an authorization themselves. And be consistent — these agents also export path telemetry to a third-party SaaS, so the case for them is authorization status, not a smaller attack surface.

For reference if a commercial tenant is ever in scope: the only INR-enabled partner solution Microsoft lists is Cisco IOS XE SD-WAN, minimum version 20.4 / 17.4. Enablement requires a Global Administrator to grant tenant-level Entra ID application permissions to the vendor.

Section 6 — Configuration

Standing up probe-based steering without INR

One thing to understand before configuring: Cloud OnRamp for SaaS does not treat probing and Microsoft telemetry as alternatives. In a commercial tenant it blends INR's opinion score into its best-path algorithm alongside its own probe results. A GCC Moderate deployment is therefore running the algorithm with one input missing — not running a parallel design. Configure accordingly, and set expectations with that in mind.

Prerequisites

Administration → Settings
Enable Cloud OnRamp for SaaS. Required in all cases.
Administration → Cluster Management
Enable Cisco SD-AVC. Required if you intend to steer by Microsoft 365 traffic category rather than a flat application list.
Administration → Settings → Cloud Services
Enable the SD-AVC Cloud Connector, which periodically fetches the Microsoft 365 Optimize / Allow / Default IP and URL categories from the Microsoft web service. From SD-WAN Manager 20.14.1 this is configured on the Cloud Services page without retrieving an OTP or opening a TAC case; earlier releases require that older path.
Transport / DIA
Direct Internet Access at each site that will probe locally. If a gateway site uses a SIG tunnel as its DIA connection, NBAR protocol discovery must be enabled in that tunnel's configuration.
Branch DNS
Name resolution occurring local to the branch egress. This is a prerequisite, not a tuning step — see below.

Configuration sequence

  1. Choose the egress model per site. The best-path algorithm selects among the configured, available Cloud OnRamp egress options — local DIA egress, gateway-site internet egress, or both. Decide this before enabling applications; it determines what the probes are comparing. A site with a single DIA circuit and no gateway alternative has nothing to steer between, and Microsoft makes the same point about INR: little value where there is no second path.

  2. Enable the applications and application lists. For Microsoft 365, select which traffic categories to optimize — typically Optimize, or Optimize and Allow. SD-AVC supplies the category membership from Microsoft's published endpoint data. Confirm the fabric is pulling the Worldwide (+GCC) instance. There is no GCC instance; a DoD or GCC High feed classifies prefixes your tenant does not use.

  3. Set the probe endpoint for each application list. Cloud OnRamp for SaaS probes a single server per list — the probe endpoint — to determine that list's best path. The endpoint may be given as a URL, probed on port 80 or 443 according to the scheme, or as an IP address. Newer releases also allow user-defined probe endpoints to be attached to applications directly in the Application Catalog. This is the step most likely to be wrong in a GCC build. A default probe endpoint aimed at a commercial hostname measures a path your users never take. Point it at an endpoint that terminates in the GCC service footprint and confirm the probe actually resolves and responds from a branch.

  4. Attach the DIA sites and gateway sites to the enabled application lists and apply the configuration.

  5. Baseline before you rely on it. Read vQoE per path: 8–10 green, 5–8 yellow, 0–5 red, derived from measured loss and latency against expected values. Cisco is explicit that the vQoE status and score shown on the monitoring page are indicators, not failover thresholds, and do not directly drive best-path determination. Do not write an operational runbook that treats the displayed score as the trigger.

Local DNS resolution

Microsoft's connectivity principles state it directly: ensure name resolution occurs close to the network egress, so connections are served through the most optimal Microsoft 365 front door. Local DNS and local internet egress are to be implemented together — Microsoft names remote lookups as a cause of network hairpins, and puts local DNS resolution alongside local egress at the top of its optimization-impact table.

Trap — local egress with central resolution

If branch clients keep resolving through centralized resolvers in the datacenter, Microsoft's Distributed Service Front Door steers on the resolver's apparent location. Packets then egress locally at the branch and travel to a front door chosen for the datacenter. The design looks deployed and delivers little.

This failure is quiet in a way the others are not: Cloud OnRamp probes will report a healthy path, because the path to that front door genuinely is healthy. It is the wrong front door. Nothing on the SD-WAN dashboard says so.

Practically: place resolvers or caching members at the DIA sites, point branch DHCP at them, and audit conditional forwarders — a forwarding rule that pulls Microsoft 365 queries back to a core resolver reintroduces the hairpin no matter how the branch is otherwise configured. Microsoft also asks that local servers cache records appropriately.

Two consequences worth carrying forward. DNS is not only a performance lever here — Microsoft states its connectivity guidance is built around domain-based endpoint identification, and that many endpoints publish no IP data at all, so resolution is part of how traffic gets classified. And if branch resolution is served by a cloud-delivered DNS security service, confirm you are pointed at its federal instance rather than its commercial one, and record which in Attachment B's Domain Name System row — the same class of error as an agent registering to the wrong ThousandEyes platform.

Vendor-specific — Infoblox DDI

Skip this block if the agency's DDI is not Infoblox; the principles above are vendor-neutral and stand on their own.

IPAM is the natural source of truth for Attachment A. The post-NAT public egress ranges the site register needs are IPAM data. Keep the reconciliation direction right: verify from the branch, then reconcile to IPAM. The site is authoritative; the record is not, and a register built from IPAM alone inherits whatever has drifted.

Local resolution means grid members or caching resolvers at the DIA sites, with branch DHCP handing out those resolvers. Then audit the grid's forwarders and forwarding rules — this is where central resolution usually survives an otherwise correct branch build.

If DNS security is cloud-delivered, confirm the federal instance. Infoblox's BloxOne Threat Defense Federal Cloud holds FedRAMP Moderate authorization, granted January 2023 with the Census Bureau as sponsoring agency. The commercial cloud is a different service. This is the Domain Name System row in Attachment B, and the failure mode is identical to an agent registering to the wrong ThousandEyes platform.

Do not assume SD-WAN Manager orchestrates Infoblox. Cisco Catalyst Center has a genuine Infoblox IPAM integration over WAPI against the Grid Master, and Infoblox NIOS 8.6.0 documents API-based integrations with Cisco Meraki and Viptela SD-WAN through Network Insight. But Catalyst Center is not Catalyst SD-WAN Manager, and Viptela is the legacy naming of what is now Catalyst SD-WAN — neither statement establishes support on your current Manager release. Put it to the vendor rather than inferring it from a version-old datasheet, and plan on manual reconciliation until someone confirms otherwise.

What to document for the ATO package

Dependency introduced — SD-AVC Cloud Connector

The Cloud Connector is a Cisco-hosted cloud service that your SD-WAN Manager reaches out to for Microsoft 365 category data. Enabling it introduces precisely the class of external-service dependency this briefing examines elsewhere — so document it deliberately rather than inheriting it. The alternative is running without Cloud Connector on static or custom application lists, trading automatic category updates for a self-contained fabric. That is a real choice with an operational cost; make it explicitly.

Architecture review — TIC 3.0

Local DIA egress at a branch relocates the Policy Enforcement Point by design. Confirm the branch egress path maps to a TIC 3.0 security pattern and that the campus PEP's capabilities have been transferred to the branch before enabling, not after. This is an architecture question, not a device-configuration question, and it is the item most likely to stall the deployment — treated in full in Section 8.

Section 7 — Deployment

ThousandEyes agents for path attribution

Scope this correctly before deploying: ThousandEyes is observability, not control. It does not feed Cloud OnRamp's best-path algorithm. Probes steer; ThousandEyes explains. Deploying agents does not restore what INR's absence costs you in path selection — it restores your ability to say why a path degraded, which is the more common operational need during an incident.

The one detail that must not be missed

ThousandEyes for Government is a standalone platform instance hosted in AWS GovCloud, not a tenant or setting inside the commercial platform. Agents must be told to register to it. For a Linux-package agent, that means adding the -m advanced option to the installation script with the value set to FEDRAMP.

An agent installed without it registers to the commercial platform. For a federal deployment that is a data-placement incident, not a configuration nit — agency network telemetry landing outside the authorized boundary. Make this an explicit build step with a post-install check that the agent appears in the government console and nowhere else.

Form factors

Linux package
Installed onto a supported distribution such as Ubuntu or Red Hat. Requires the -m advanced / FEDRAMP option above.
Docker container
64-bit Linux host, kernel 3.10 or later, with cgroups and network namespaces. The government instance imposes additional prerequisites on Docker installs — take them from the ThousandEyes for Government documentation, not the general Docker page. The account group token is supplied through TEAGENT_ACCOUNT_TOKEN. Docker for macOS and Docker for Windows are not supported for production.
Virtual Appliance (TEVA)
A prepared VM carrying both the operating system and the agent. The lowest-friction option where branch virtualization already exists.
Embedded on Catalyst routers
A Docker-type container run through IOx application hosting on IOS XE Catalyst SD-WAN devices. Minimum 8 GB DRAM; provision 16 GB to co-host applications such as UTD or DRE.
Sizing trap — read this against Section 8

The TIC capability-transfer obligation tends to put UTD on the same branch router you are now asking to host a ThousandEyes agent. IOx will not run additional applications when CPU, memory or storage are short — it raises an error and declines. A branch sized at 8 GB satisfies the agent alone and then fails the moment the security stack arrives. Size for the finished architecture, not for the first component you deploy.

What to measure

Aim the tests at the gap INR leaves rather than duplicating what Cloud OnRamp already probes. HTTP Server and Page Load tests against the Microsoft 365 endpoints your tenant actually uses give service-side experience; Network tests with Path Visualization per circuit give hop-level attribution when a path degrades; agent-to-agent tests across the fabric separate a transport problem from a SaaS problem.

Baseline all of it before cutting over to local DIA. Without a pre-change baseline, the first complaint after cutover has no comparison and the design gets blamed on principle.

Verify before designing around it

Open question: whether the SD-WAN Manager-driven embedded agent path supports the government instance. Explicit FedRAMP prerequisites are documented for the Linux package and Docker methods; the Cisco device app-hosting path could not be confirmed either way from available sources. From SD-WAN Manager 20.14.1 the Manager can reach Cisco services in the Cisco Networking Cloud including ThousandEyes, and ThousandEyes supports agents on Catalyst routers in SD-WAN mode — but neither statement establishes government-instance support.

Confirm with Cisco before building the design on embedded agents. If the answer is no, the fallback is standalone agents at each site, which changes branch hardware and licensing assumptions materially. That is a question to ask in week one, not week ten.

Section 8 — Architecture

TIC 3.0 and PEP alignment

This section is independent of whether INR exists — a commercial tenant running full INR faces identical obligations. It bears on everything above it, the ThousandEyes agents included: they egress to an external platform like any other branch traffic. If the deployment stalls, this is where it stalls, and it is not a Microsoft or Cisco problem to solve.

Identify the pattern before the capabilities

The TIC 3.0 Branch Office Use Case defines three security patterns: Branch Office to Web, Branch Office to Agency Campus, and Branch Office to Cloud Service Provider. An agency may implement a subset rather than all three. The stated purpose is to eliminate the “TIC tax” of hairpinning outbound internet traffic back to a central perimeter — which is the same objective the SD-WAN design is pursuing.

Classification — get this right first

Microsoft 365 Optimize traffic egressing locally is Branch Office to Cloud Service Provider: an agency-sanctioned CSP. It is not Branch Office to Web. The distinction is not bookkeeping — it determines which PEP capabilities apply. Filing M365 DIA under the Web pattern tends to pull in a general web-proxy capability set, and inspecting the Optimize endpoints is precisely what that category exists to avoid. Misclassify here and the architecture review will hand back requirements that negate the performance case for the whole project.

The transfer obligation

The governing constraint is straightforward: under a DIA architecture, branch performance improves, but all of the security applied at the campus PEP must be transferred to the branch. TIC 3.0 permits PEPs to sit between, before, or within a trust zone, so the branch becomes a trust zone with enforcement at its own edge. Work the transfer explicitly rather than assuming the SD-WAN appliance covers it.

PEP capability group What branch DIA changes What to record

Microsoft asks that Optimize endpoints bypass TLS break-and-inspect and packet inspection. A campus web PEP normally performs exactly that. Nothing in the SD-WAN configuration resolves this; it is an agency risk-acceptance decision, scoped to a named endpoint set and signed by someone empowered to sign it. Briefings that leave this implicit are the ones that come back from review. Put it in front of the AO as a decision with a bounded scope, early.

Section 9 — Sequencing

Order of work, and why this order

The instinct on a project like this is to start with the SD-WAN configuration, because it is the part the network team controls outright. That is the wrong start. The critical path runs through two external answers — an Authorizing Official's decision on inspection bypass, and Cisco's answer on government-instance support for embedded agents — and both of them change what hardware you buy. Configuration is fast and reversible. Procurement and risk acceptance are neither.

0Days

Disconfirm the premise

Open a GCC Moderate tenant at Health → Network connectivity → Settings and confirm the SD-WAN solution pane is absent. Five minutes, first-party, and it costs nothing to be wrong early rather than late.

Exit: INR confirmed unavailable in your own tenant, not merely in documentation. If the pane is present, stop — the rest of this plan is the wrong plan.
1Week 1

Open the long-lead questions, all in parallel

Long lead

Four items, none of which the network team can answer alone, and each of which gates something downstream. Put the TIC classification — Branch Office to Cloud Service Provider, per Section 8 — to the architecture review. Put the Optimize-category inspection bypass in front of the AO as a scoped risk acceptance. Decide whether the SD-AVC Cloud Connector dependency is acceptable or whether you run on static application lists.

Exit: enough answers to size branch hardware. Specifically: do agents run embedded or standalone, and does UTD land on the same router?

How to read this section

Unlike the rest of this briefing, the sequencing above is engineering judgment rather than sourced fact — it carries no evidence grade because there is no document to grade it against. The dependencies it encodes are real and traceable to earlier sections; the phase boundaries and durations are a recommendation, and a programme with different procurement or review timelines should reorder accordingly.

The two claims worth arguing with, if you disagree with anything here: that Phase 1 must complete before Phase 2 rather than running alongside it, and that Phase 3 must complete before Phase 4. Both are there because the failure they prevent is expensive and unrecoverable, not because the sequence is naturally tidy.

Section 10 — Rollback

What reverses, what leaves residue, and what does not reverse at all

Treating this deployment as one thing you can back out of is the mistake. It is several changes with very different reversibility, and the ones that do not reverse are not the ones teams worry about in advance. Decide the thresholds and the decision rights before cutover — during an incident, “is this bad enough to roll back?” becomes an argument rather than a determination.

Change Reversibility How, and what remains
Local DIA steering at a site Clean Revert the SD-WAN policy for that site; traffic returns to backhaul through the campus PEP. Per-site and fast. No residue.
Application lists and probe endpoints Clean Disable the enabled applications or correct the probe endpoint. Misclassification stops as soon as the policy is withdrawn.
Inspection-bypass exemption at the campus PEP Needs deliberate reversal Does not revert with the routing change. Withdraw the exemption scope explicitly and tell the AO it has been withdrawn — see the trap below.
SD-AVC Cloud Connector Residue Can be disabled, but the Cisco cloud dependency was established and exercised. Disabling also freezes Microsoft 365 category data, so application lists go stale from that moment — plan how they are maintained if you turn it off.
ThousandEyes agents Residue Agents uninstall cleanly. Telemetry already sent does not. If an agent registered to the wrong platform, removal is containment, not rollback.
Pre-cutover baseline window Irreversible Cannot be recreated. If Phase 3 was skipped, no rollback restores the ability to say what changed.
Branch hardware Irreversible Procurement does not roll back. This is why the sizing question sits in Phase 1 rather than Phase 4.

Decide the triggers before cutover

Write the thresholds against the Phase 3 baseline, in the units ThousandEyes and Cloud OnRamp already report, and name who holds each decision. Three distinct classes, with different urgency and different decision-makers:

  1. Performance regression at a site. Measured degradation against that site's own baseline, sustained rather than momentary. Network operations reverts that site's steering. No approval cycle — this must be a routine, local, same-shift action or it will not happen when needed.

  2. Compliance or security finding. The exemption scope turns out wider than approved, branch telemetry is not reaching CLAW, or a capability named in the transfer table is not actually in place. Not a network decision. Revert the affected sites, notify the AO, and treat the gap as a finding — the routing change is the fastest thing you can undo while the underlying issue is worked.

  3. Wrong-platform agent registration. An agent appears in the commercial console. Handle as a data-placement incident under the agency's existing procedure, not as a deployment rollback. Removing the agent stops further flow; it does not address what already went. Escalate on the agency's timeline, not the project's.

Trap — reverting the route but keeping the exemption

Rolling back to backhaul restores the campus PEP as the enforcement point, so the TIC posture is restored by the rollback rather than degraded by it. That part is genuinely safe. What is not safe is leaving the Optimize-category inspection exemption in place afterwards: the traffic is once again traversing the campus PEP, but with an exemption that no longer buys anything. You keep the accepted risk and lose the performance it was accepted for. Make withdrawal of the exemption an explicit, tracked step of any rollback, not an implied consequence.

Trap — rolling back the observability with the change

The instinct during a bad cutover is to revert everything that was touched. Leave the ThousandEyes agents running. They are how you establish what actually went wrong, and they are the only thing that will tell you whether the second attempt is better. Reverting the monitoring alongside the change is how a deployment gets rolled back twice for the same unexplained reason.

How to read this section

Like Section 9, this is engineering judgment rather than sourced fact, and carries no evidence grade. The reversibility classifications follow from how each component works as documented in Sections 6 through 8; the thresholds and decision rights are yours to set, and they are the part most worth arguing over before cutover rather than after.

Section 11 — Communications

Briefing the Authorizing Official

This programme contains exactly one decision that requires an AO signature. Everything else is either informational or belongs to somebody else. The most common way this meeting goes wrong is arriving with “approve the SD-WAN project” — which invites the AO to adjudicate vendor questions, procurement and architecture all at once, and produces a deferral rather than a decision.

The ask, in one sentence

Accept the risk of exempting the Microsoft 365 Optimize endpoint set — enumerated from the Worldwide (+GCC) feed — from TLS break-and-inspect at branch direct-internet egress, for a named list of pilot sites, with compensating controls identified and branch telemetry continuing to reach CLAW.

Bounded four ways: a specific endpoint set, a specific list of sites, named compensating controls, and per-site reversal within a shift. If any of those four is missing from the memo, the ask is not yet ready to put in front of an AO.

Anticipate these four questions

  1. “What can you no longer see?” Content inspection on the Optimize endpoints, specifically. Say it plainly rather than reaching for the word “bypass” and hoping it passes. Then name what covers it: tenant-side controls such as Defender for Office 365 and DLP, Conditional Access, endpoint controls, and ThousandEyes path evidence. Section 8's transfer table is the exhibit.

  2. “How large is the exemption, and does it drift?” This is your strongest answer, so do not bury it. The scope is a published, machine-readable list, and Microsoft publishes additions 30 days before they become active. It is an enumerable set with change notice — not an open-ended trust grant. Commit to a review cadence tied to the feed's monthly updates.

  3. “What happens if this turns out badly?” Per-site reversal, same shift, no approval cycle. Rolling back restores the campus PEP as the enforcement point, so the TIC posture is restored rather than degraded. State the accompanying commitment: withdrawing the exemption is a tracked step of any rollback, not an implied consequence. Section 10.

  4. “Is this a FedRAMP question?” No — and be ready to explain why, because the framing is common. The exemption is an agency risk decision about inspection at your own egress. FedRAMP boundary rules govern a provider's assessment scope. Letting the FedRAMP framing in reintroduces exactly the error Section 2 corrects, and hands the AO a question that is not theirs to answer.

Do not bring these to the AO

The INR unavailability story as a compliance matter. It is product availability in a sovereign cloud. Presenting it as a FedRAMP or boundary issue invites a compliance debate the programme does not need and cannot win, because the premise is wrong.

Vendor and procurement questions. Whether the embedded ThousandEyes agent supports the government instance is a Cisco question. Branch DRAM sizing is a procurement question. Neither improves by being raised at this table.

Any claim that probing replaces INR. If you tell the AO the capability has been restored, you will be held to that when a service-side degradation goes undetected. It has not been restored; the observability gap is narrowed and the steering input is absent.

Return to the AO when

Record these triggers in the decision memo itself, so returning is a pre-agreed step rather than a renegotiation: the exemption scope widens beyond Optimize; sites are added outside the approved list; a compensating control named in the memo turns out not to be in place; or the exemption is withdrawn during a rollback.

Disclose the open items yourself

Section 12 lists what this briefing could not confirm. Put the relevant ones in the memo rather than letting the AO's staff find them. An AO who discovers an undisclosed gap discounts everything else in the package, including the parts that are well evidenced — and this package's credibility rests on the discipline of saying what is documented, what is inferred, and what is unknown.

Engineering and programme judgment, not sourced fact, and not legal or compliance advice. Your agency's risk-acceptance process, delegation of authority and memo format govern; adapt the structure to them. The part worth keeping regardless of local process is the discipline of a single bounded ask with a stated reversal path.
